# Profile — ultimate-sitemap-parser @ v1.8.1 (baseline)

Generated by `bench/profile.py` against the replay corpus
(`bench/corpus/manifest.json`, 250 gzipped sub-sitemaps from
`play.google.com`, fanout_cap=200). All measurements are **REPLAY**
mode; no live Google traffic.

## Setup

- Python 3.11.15, usp 1.8.1, 20-core Linux, no `uvloop`.
- Profile `zero` = 0ms ± 0 latency, 0% errors. Measures pure CPU.
- Profile `vn-google` = 180ms ± 40ms latency, 0% errors. Mimics Hanoi
  edge to Google.
- `fanout_cap=200` means: at each sitemap index level, the recursive
  crawl is capped to the first 200 entries (sorted). With 2 index
  files → 400 sub-sitemaps fetched per run.
- All times in seconds. `parse_s` is wall time spent inside the XML
  parser; `fetch_s` is the rest.

**Phase 7 gate answer:**

> *“zero: expat chiếm bao nhiêu % CPU? (nếu < 25% → Phase 7 bị huỷ)”*

**Phase 7 stays open.** Optimizing the parse path (lxml, free-threaded

## Wall-time breakdown — `vn-google` cap=200 (130s total)

With 180 ms ± 40 ms per HTTP RTT and sequential fetching, the picture
flips: socket wait dominates. The Phase 3 async rewrite should swing
this.

| Bucket | Estimated s | % |
|---|---:|---:|
| Socket wait (180 ms × 403 req) | ~75 | 58% |
| XML parse | ~50 | 38% |
| Gunzip | ~2 | 2% |
| Other | ~3 | 2% |

→ Phase 3's north-star target: `urls_per_s` @ `vn-google` ≥ **10×**
baseline (currently **602 urls/s**; target ≥ **6020 urls/s**).

## Tempfiles

`tempfile.mkstemp` is monkey-patched and counted via
`bench/profile.py --mode tempfile`:

- `tempfile-count-zero-cap200.txt` = **200**

Each `PagesXMLSitemap` opens its own tempfile via `mkstemp`, dumps its
pages with `pickle.dump`, and lazily reloads on `.pages` access. Two
issues identified (matches MASTER-PLAN §0 #6):

1. 200 file descriptors opened during a 400-sub-sitemap crawl —
   inefficient and pressure-y.
2. Pickle dump + reload on every `.pages` traversal — slow, doubles
   memory during the `all_pages()` walk.
